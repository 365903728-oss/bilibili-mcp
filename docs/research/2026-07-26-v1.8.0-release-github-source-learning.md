Seven-area trace:

1. **Source of truth and state model:** Semantic-release supplies `nextRelease.version` and `channel`; the package at the repository root or `pkgRoot` supplies name, existing package fields, and publish configuration. `prepare` delegates version and lockfile synchronization to the npm CLI with `--no-git-tag-version --allow-same-version`. Identity is package name, version, registry, and dist-tag. Unknown package fields remain under npm's normal rewrite behavior.
2. **Execution path and callers:** Semantic-release calls the hooks exported by `index.js`. `verifyConditions` validates configuration and authentication; `prepare` versions the package and optionally creates a tarball; `publish` invokes `npm publish` with an explicit base path, user config, tag, and registry; `addChannel` invokes npm dist-tag operations. Registry selection is centralized in `get-registry.js`.
3. **Failure semantics:** Invalid options, missing package metadata, and authentication errors become aggregated `SemanticReleaseError` values. Official-registry OIDC detection falls back to npmrc/token authentication when unavailable. npm subprocess and network failures propagate. There is no general retry, cancellation, transactional rollback, or automatic restoration after package version mutation; a successful registry publish is externally irreversible.
4. **UI boundaries:** Not applicable. This is a CLI plugin; its human boundary is logged progress plus streamed npm stdout/stderr.
5. **Verification:** AVA/C8 tests cover version/lock updates, root and subdirectory packages, private/skip-publish behavior, registry selection, dist-tags, token auth, OIDC exchange, and a Verdaccio-backed integration path. CI runs clean install, signature audit, and tests across Node 22.14, floating 22, and 24. At this pinned head, the release workflow succeeded while the floating Node 22 matrix leg failed with only an exit status available; fixed 22.14, 24, and development-version jobs passed. This is mixed evidence and prevents treating the upstream workflow as copy-ready.
6. **Dependencies and runtime:** The manifest requires Node `^22.14.0 || >=24.10.0` and declares npm `11.18.0`; lockfile v3 pins the dependency graph. Production uses npm subprocesses, registry/OIDC network calls, temporary npmrc files, package/lockfile writes, and optional tarball movement. There is no install/postinstall hook; published files are limited to `lib` and `index.js`. Integration tests additionally require Docker and network access.
7. **Governance and provenance:** MIT license. The non-truncated tree has no `SECURITY.md`, `NOTICE`, `.gitmodules`, or submodules. The public security-advisory endpoint returned no advisories; private dependency-alert state was not accessible. The package enables provenance, and its release workflow grants OIDC permission, but it also retains an npm-token fallback. No external source is copied into this project.

Entry-to-failure trace:

`semantic-release hook` → `index.js` → `verifyConditions`/`prepare`/`publish` → npm CLI or OIDC/registry call → propagated subprocess/network error or structured configuration/authentication error. The OIDC exchange is a preflight; the locked npm CLI performs native trusted publishing from the CI OIDC environment.

Registry and scope are input-derived; the generated npmrc is the adapter state.
2. **Execution path and callers:** The Action runtime enters `src/setup-node.ts`. When `registry-url` is provided, it calls `authutil.configAuthentication`, which normalizes the registry, preserves unrelated registry lines, writes an npmrc under `RUNNER_TEMP`, and exports `NPM_CONFIG_USERCONFIG`. It exports `NODE_AUTH_TOKEN` only when the caller already supplied that variable.
3. **Failure semantics:** Top-level setup catches failures and marks the Action failed. File-write, input, download, cache, and tool-install failures are not silently converted to success.
