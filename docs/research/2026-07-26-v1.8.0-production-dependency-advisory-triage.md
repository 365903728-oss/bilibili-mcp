## Findings

The exact production inventory contained 94 package names. The official npm bulk advisory endpoint returned four advisories across three installed packages:

| Advisory | Installed path | Severity | First patched version | Static reachability verdict |
|----------|----------------|----------|-----------------------|-----------------------------|
| `GHSA-frvp-7c67-39w9` | root → MCP SDK 1.27.1 → `@hono/node-server` 1.19.14 | moderate | 2.0.5 | Not actionable, high confidence |
| `GHSA-v422-hmwv-36x6` | root → MCP SDK 1.27.1 → Express 5.2.1 → `body-parser` 2.2.2 | low | 2.3.0 | Not actionable, high confidence |
| `GHSA-v2hh-gcrm-f6hx` | root → MCP SDK 1.27.1 → Ajv 8.20.0 → `fast-uri` 3.1.2 | high | 3.1.4 | Not actionable, medium confidence |
| `GHSA-4c8g-83qw-93j6` | root → MCP SDK 1.27.1 → Ajv 8.20.0 → `fast-uri` 3.1.2 | high | 3.1.3 | Not actionable, medium confidence |

- `npm audit --omit=dev --json` did not produce parseable JSON in this environment. The official endpoint returned a gzip body without metadata that allowed the tested npm CLI paths to decode it. This is a transport/tooling failure, not a clean audit result.
- The fallback used npm's resolved omit-dev dependency graph to create the exact bulk-advisory request and manually decoded the official response. No third-party advisory source was substituted.
- The Hono advisory requires an attacker-controlled HTTP path to reach a Windows static-file handler. This project imports and connects only `StdioServerTransport`; it does not expose Hono streamable HTTP or serve-static.
- The body-parser advisory requires an Express/body-parser HTTP route configured with an invalid limit. This project does not instantiate Express, body-parser, or an HTTP request-body parser.
- Ajv can load `fast-uri` inside the MCP SDK runtime, but this project supplies fixed developer-authored schemas, contains no client-controlled `$id`/`$ref` path, does not use MCP elicitation, and makes no authorization, allowlist, origin, or network-fetch decision from a parsed hostname.
- Codex Security rendered a complete `triage-finding/v0` result for all four advisories. The two HTTP findings are high-confidence `not_actionable`; the two runtime-reachable Ajv findings are medium-confidence `not_actionable` because the vulnerable package loads but the required untrusted source and security-sensitive sink are absent.

## Risks And Unknowns

- No repository `SECURITY.md` formally declares stdio-only transport and trusted local schemas as supported boundaries.
- Static reachability does not remove the vulnerable versions from the dependency graph.
- The latest MCP SDK observed during this review still allows the vulnerable Hono 1.x line; a safe refresh may require an upstream SDK release or a separately verified major-version override.
- npm registry response encoding behavior may differ in GitHub Actions, so the normal workflow audit behavior must be rechecked rather than inferred from this local CLI failure.

## Remediation Decision

Live package metadata and the two open SDK issues establish the narrowest safe split:

- `body-parser@2.3.0` satisfies Express 5.2.1's existing `^2.2.1` range.
- `fast-uri@3.1.4` satisfies Ajv 8.20.0's existing `^3.0.1` range.
- Both can be fixed through a lockfile-only refresh; no direct dependency or override is needed.
- Every Hono 1.x release remains inside the advisory range. Hono 2.0.5+ clears the advisory but requires Node 20, while this package and MCP SDK 1.x both promise Node 18.
- The SDK imports only `getRequestListener`; the vulnerable `serveStatic` export is not referenced, and this project uses only stdio.

Decision:

- Refresh only `body-parser` and `fast-uri` inside their already-declared compatible ranges.
- Do not force a Hono 2 override, do not raise the package's Node minimum, and do not downgrade the MCP SDK.
- Retain the Hono advisory as an explicit accepted non-actionable risk until upstream widens the range or provides a Node 18-compatible fix.
