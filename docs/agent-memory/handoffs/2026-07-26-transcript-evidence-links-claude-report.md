## Diff Notes

- `resolvedPage` was previously computed lazily inside the success path and re-evaluated as `page ?? matchPartIdentity(...).page` in every fallback branch. It is now computed once, right after `resolvePartCid`, which is the recommended approach in the handoff. Behavior is unchanged because `matchPartIdentity` is deterministic in `(videoData.cid, pages)` and the `?? page` short-circuit preserved any caller-supplied `page` previously; the consolidated `resolvedPage` is identical to all prior expressions.
- `buildTranscriptSourceUrl` preserves the exact `extractBVId` casing by embedding `bvid` directly in the URL pathname template. The uppercasing `normalizeBVId` / `createVideoUrl` helpers are intentionally not used, per the research note and handoff.
- `pages.length > 1` is the trigger for appending `p=<resolvedPage>`. Single-Part videos (including `pages.length === 0`) produce `https://www.bilibili.com/video/<bvid>/` with no query string.
- Per-match `timestamp_url` reuses the same root `source_url` and sets `t` via `searchParams.set`, so multi-Part matches serialize as `?p=<page>&t=<from>` in insertion order, matching the research evidence `https://www.bilibili.com/video/BV153411j7Ys/?p=2&t=17`.
- `String(hit.from)` preserves decimal seconds (`String(12.5) === "12.5"`) and integers (`String(17) === "17"`), matching the live evidence that decimal `t` survives Bilibili's player.
